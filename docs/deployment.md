# 部署 U60 Pro Dash

本 fork 的部署入口是仓库根目录的 `dash.sh`。它一起构建、校验和部署两个程序：`zte-agent` 提供 Web/API 和网络服务管理，`u60-screen` 提供机身显示与触摸。网页已嵌入后台二进制，不需要第三个 Web 服务。

## 安装与升级

设备需要先有可用的 root ADB（或 SSH）、已配置密码并正在运行的后台，以及现有开机启动文件。脚本适配 U60 Pro/B31 的显示与启动路径；它不是原厂设备的解锁或刷机工具。首次接入后台仍使用 `setup.sh`，后续使用本页命令。

电脑需要 Bash、Python 3.11+、Rust、`aarch64-unknown-linux-musl` 标准库、ARM64 交叉链接器，以及 ADB 或 SSH 客户端。脚本优先复用 `~/.local/share/u60-build/` 的工具链，也支持 `U60_BUILD_ROOT`、`CARGO`、`CARGO_HOME`、`RUSTC`、`CARGO_TARGET_AARCH64_UNKNOWN_LINUX_MUSL_LINKER`。构建依赖与链接器说明见 [原生屏幕开发](../u60-screen/NATIVE.md)。

在仓库根目录运行：

```bash
bash dash.sh check       # 只读：连接、权限、启动同步、空间和恢复条件
bash dash.sh install     # 构建并部署后台 + 机身界面，启用开机启动
bash dash.sh status      # 查看版本组、进程、屏幕首帧和回退结果
```

升级也是同一个 `install` 命令。后台密码由设备内的迁移助手保留；不要把密码附在命令后面。Tailscale 登录身份、网关设置、后台业务配置、屏幕外观与锁屏密码继续使用设备上的原有文件。部署会重启后台，Web 会话需要重新连接，后台管理的网络服务可能短暂中断。

使用 SSH 时，每条设备命令都加上连接参数；需事先配好 SSH 密钥并确认服务器指纹：

```bash
bash dash.sh check --ssh root@192.168.0.1 --port 2222
bash dash.sh install --ssh root@192.168.0.1 --port 2222
bash dash.sh status --ssh root@192.168.0.1 --port 2222
```

ADB 多设备环境使用 `--serial` 或 `ANDROID_SERIAL`。首次常驻部署应在能接触设备且 ADB 可用时进行；SSH 无法恢复 USB、系统内核或供电故障。

## 常用管理命令

| 命令 | 效果 |
| --- | --- |
| `bash dash.sh build` | 仅构建，产物写入 `target/dash/`，不访问设备 |
| `bash dash.sh install --no-build` | 安装已有部署包，仍检查全部哈希与 ARM64 静态 ELF |
| `bash dash.sh stop` | 恢复原厂屏幕，停止自定义屏幕自启，保留项目后台供远程管理 |
| `bash dash.sh start` | 重新启动项目后台与机身界面，恢复屏幕自启 |
| `bash dash.sh rollback` | 切回上一组项目版本，重新执行健康观察；首次安装无上一组时用 `restore` |
| `bash dash.sh restore` | 恢复首次部署前的后台二进制、启动文件和原厂屏幕 |

构建与安装可加 `--offline`，要求 Cargo 依赖已缓存。`--artifacts /path/to/package` 可指定部署包目录。包中的两个二进制、管理脚本和 SHA-256 清单共同决定版本组 ID；不要单独替换其中一个文件。

`start`、`stop`、`rollback`、`restore` 返回的是设备操作及当时状态；后台启动或回退观察可能仍在进行，可稍后再运行 `status`。`restore` 不删除项目备份，也不撤销部署后修改的 Wi-Fi、Tailscale、代理服务等业务配置。

## 启动与恢复

原厂屏幕仍参与固件的早期启动同步；脚本等待同步完成，验证新后台的认证与实时数据，再停止原厂界面并接管显示。它不会禁用原厂 UI 的启动注册，不会修改固件分区或守护进程同步名单。

部署先保存原后台和启动文件、校验上传文件，再写入待确认版本记录。新后台与屏幕要保持存活、提交首帧并持续更新事件循环心跳；30 秒后还会检查原先健康的 Tailscale 是否恢复同一运行模式，以及原先运行的代理服务是否恢复。检查失败会恢复上一组；首次部署失败则恢复原安装。观察期间掉电，下次启动优先恢复上一组。

启动验证先等待 HTTP 监听并验证密码，再使用新的认证会话检查实时数据。恢复原后台后也会验证 HTTP 与认证，失败时明确报告需要处理，不把恢复了文件当成服务已恢复。`install_exit=0` 只代表启动命令已返回；最终以健康观察结果为准。

Tailscale 内核网关的远程 Web 使用 `9091`，本机及热点访问使用 `9090`，避免两个服务争用端口。后台启动时只迁移指向本机管理 API 的旧 Serve 转发；详见 [网络服务管理](network-services.md)。

独立恢复进程监控屏幕与管理进程。常驻屏幕退出或心跳停滞时，它恢复原厂界面及原亮度；已确认版本的后台继续运行。恢复失败会保留错误信息。这个机制不能承诺设备永远不会黑屏或失联；供电故障、文件系统损坏、内核故障及长期功耗仍需要实机验证。

单后台 OTA 在成对部署模式下停用，Web 的更新页会提示使用 `dash.sh`；旧 `setup.sh`、`deploy.sh` 和功耗测量部署入口也会拒绝覆盖正在使用的成对版本。

## 文件与排查

设备文件集中在 `/data/u60-dash/`：

| 路径 | 用途 |
| --- | --- |
| `releases/<id>/` | 同一版本组的两个程序、恢复脚本与校验清单 |
| `current`、`previous`、`pending` | 当前、上一组与待确认版本 |
| `original/` | 首次部署前的后台和启动文件备份 |
| `agent.env`、`health.json` | 仅设备 root 可读的运行环境与健康检查基线 |
| `install.log`、`service.log`、`last-error` | 部署与恢复诊断 |

不要发布 `agent.env`、`original/startup.sh` 或设备日志；其中可能含原配置和身份信息。仓库只保存代码与示例，不回传设备密码。

若连接在安装途中断开，恢复连接后先运行 `bash dash.sh status`；观察与回退在设备内独立执行，不依赖电脑保持连接。不要反复运行旧部署脚本。预检查要求 `/data` 至少有 150 MiB 空间，留存的新旧版本不会自动清理。

部署管理器脚本本身发生变更时，脚本会拒绝直接替换正在使用的管理器。先运行 `bash dash.sh restore`，确认已恢复，再运行新的 `bash dash.sh install`；首次原始备份仍会保留。

如果首次安装在创建版本状态前失败（例如旧脚本使用了固件 BusyBox 不支持的 `flock -w`），更新代码后重新运行 `bash dash.sh install` 即可。安装器会在确认没有运行中或待确认版本、原启动文件尚未被接管，并取得部署锁后替换旧管理脚本；不需要删除部署目录或执行旧版 `restore`。锁等待仅使用固件支持的 `flock -n`。

## 验证范围

自动化测试覆盖部署/升级/回退、停止与恢复、校验失败不修改启动、屏幕失败、屏幕停滞、管理进程被杀、网络健康检查失败、待确认版本断电恢复，以及直启与 OTA 符号链接布局。恢复测试使用本地模拟固件和真实子进程，不操作路由器。

U60 Pro/B31 已通过只读部署预检查；常驻安装、真实重启恢复和长时间运行尚未进行实机验证。之前已验证的显示、触摸和限时试运行见 [原生屏幕](../u60-screen/NATIVE.md)。
